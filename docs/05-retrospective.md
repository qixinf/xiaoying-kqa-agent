## 2. 最难的问题

【待填写：用你自己的话写 1 到 2 个。下面是从开发过程中整理出的候选，挑你真正有体会的改写】

**候选 A："状态正确"不等于"做对了"。**
最终状态是可以自动比对的，但 C11 有两次状态正确、过程却有问题：一次用"如果你问的是……"代替用户做选择，一次在追问里报出未经读取的数字。只看通过率发现不了，必须逐条读 Trace。这改变了我对"评测"的理解：自动断言只能检查结构，过程质量需要人看，再把看到的问题转成新的代码规则。

**候选 B：决策要交给模型，边界要留在代码里，两者如何划分。**
题目要求"模型调整下一步"，同时禁止"固定条件分支、自动重试"。重试上限一开始只写在 prompt 里，模型完全可以无视。如果写成代码自动重试，又会变成"预设决策"。最终的方案是：代码只改变**模型看到的观察结果**（retryable 从 true 变为 false），由模型自己决定停止。校验器打回 finish 也是同样的思路。

**候选 C：引用真实，回答仍然可能是错的。**
逐字引用校验能防止编造原文，却防不住"引用 D01 的 30 天，回答写 15 天"。数字溯源是一个便宜但有效的补丁，但它也暴露了"引用支持结论"这件事，本质上需要语义判断。

## 3. 学习收获

【待填写：用你自己的话写。可以参考以下方向】
- 工具的错误信息是写给模型看的：`retryable`、"剩余重试次数"、"请改写查询"这些提示，直接影响模型的下一步动作。
- 检索前提要写成测试（`test_retrieval.py`），否则数据一改，用例就会悄悄失效。
- 每次修改都单独存档运行结果，迭代过程本身就是最好的评估材料。

## 4. 下一步

按优先级排序：

1. **扩充用例并多次重复运行**：每个验收点 3 到 5 种说法，每个用例跑 5 次，用通过率代替单次的通过或失败。
2. **"引用支持结论"的语义校验**：用另一次模型调用或 NLI 模型判断引用是否蕴含结论，替代或补充数字溯源。
3. **混合检索**：BM25 加向量检索，用 RRF 融合，减少模型改写查询的次数；用 C04 这类口语问题对比改写次数和延迟。
4. **冲突处理结构化**：conflict 时输出结构化的候选列表（文档、说法、适用范围、版本），方便前端展示和用户选择。
5. **迁移评估**：如果需要长流程或人工审批，迁移到 LangGraph，复用 tools 和 validator。
