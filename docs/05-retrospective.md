## 2. 最难的问题

最难的是意识到"状态正确"不等于"做对了"。baseline 跑出 10/11 后，修好 C11 的 prompt，第二轮看上去 6/6 全过。但我逐条读 Trace 时发现，有一次追问里直接报出了"600 元、400 元"，而模型根本没读过原文。自动比对只检查状态，抓不到这种问题。最终我把它转成了一条代码规则（追问中的数字也必须有引用），第三轮就在真实运行中看到它生效：模型被打回后补读了原文。


## 3. 学习收获

以前做 RAG 时，我关注的是召回率和答案质量；这次体会到，Agent 的工具返回值本身就是给模型的"提示"。retryable、剩余次数、"请改写查询"这些字段，直接决定了模型下一步怎么做。另外，把每次运行都存档，让我能清楚说明每次修改带来了什么变化，而不是只交一个最终的 11/11。

## 4. 下一步

按优先级排序：

1. **扩充用例并多次重复运行**：每个验收点 3 到 5 种说法，每个用例跑 5 次，用通过率代替单次的通过或失败。
2. **"引用支持结论"的语义校验**：用另一次模型调用或 NLI 模型判断引用是否蕴含结论，替代或补充数字溯源。
3. **混合检索**：BM25 加向量检索，用 RRF 融合，减少模型改写查询的次数；用 C04 这类口语问题对比改写次数和延迟。
4. **冲突处理结构化**：conflict 时输出结构化的候选列表（文档、说法、适用范围、版本），方便前端展示和用户选择。
5. **迁移评估**：如果需要长流程或人工审批，迁移到 LangGraph，复用 tools 和 validator。
