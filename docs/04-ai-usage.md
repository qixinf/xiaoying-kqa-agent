## 3. 本人的修改与决策

- **`tests/test_llm.py`**：AI 生成的测试直接 import httpx，用它构造假的 HTTP 400 响应，来测试 BadRequestError 的处理逻辑。本人在本地运行 pytest -q 时，收集阶段报错 ModuleNotFoundError: No module named 'httpx'。排查后发现，本地安装的 openai 版本是 3.42.1，它的底层 HTTP 库已经从 httpx 换成了 httpx2，所以环境里不再有 httpx；而测试代码直接依赖 httpx，requirements.txt 里却没有列出它，属于"隐式依赖"。本人先确认了 BadRequestError 构造时会从响应对象上读取哪些字段（request、status_code、headers），再改为用 SimpleNamespace 构造一个只包含这些字段的假响应。这样测试不再依赖任何具体的 HTTP 库，openai 以后再更换底层库也不会受影响。
- **重试上限**：工具层最初只在 prompt 里写了"服务不可用时可重试 1 次"。本人提出疑问：重试 1 次会不会太少？分析结果是，在 max_steps = 8 的预算下，正常路径需要 3 步，冲突路径需要 3 到 4 步，每次重试多占一步；如果允许重试 2 次，再碰上一次查询改写或 finish 被打回，就会耗尽步数，返回 incomplete，给用户的信息反而比明确的 tool_failed 更少。所以 1 次是合理的默认值。但分析中也发现，这个上限只是 prompt 里的一句话，模型可以无视。本人决定改为由代码强制：ToolBox 按工具统计连续的服务失败次数，额度用完后返回的 retryable 变为 false；默认 1 次，可以通过 --max-retries 配置。停不停仍由模型决定，代码只是不再给出"可以重试"的信号，所以不会退化成写死的自动重试。真实运行中，C07 在额度用完后立即返回了 tool_failed。


## 4. 验证方式

AI 生成的代码不能直接视为正确。本项目的验证分三层：

1. **离线测试**：77 个测试由 AI 生成。本人在本地运行全部通过（`pytest -q`）。读过 test_agent.py 和 test_tools.py 中与关键缺陷相关的测试（引用伪造、数字溯源、重试额度）。故意把 validator 中的逐字校验注释掉，确认对应测试会失败。
2. **真实模型运行**：本人用自己的 OpenAI Key 在本地跑了 5 轮（运行记录见 `examples/runs/index.md`）。每轮的 Trace 都经过逐条检查，不只看状态是否通过。正是这样发现了两个"状态通过、但过程有问题"的情况：C11 用假设句式作答，以及追问里夹带未经核实的数字（见 `03-evaluation.md` 第 4 节）。
3. **抽查关键 Trace**：逐条打开了 C02、C08、C11 的 Trace：核对 C02 两条引用分别来自 D01、D02 的原文；核对 C08 的判定依据是 D06 中"替代 D05"的原句；核对 C11 每次运行的路径，发现了两次"状态正确但过程有问题"的情况。

## 5. 对 AI 输出的判断原则

- AI 给出的方案，只有在能讲清楚理由并有测试覆盖时才接受。
- 关于真实模型行为的结论，只以本地真实运行的 Trace 为依据，不采信 Mock 或 AI 的推测。
